### 1-3. 채팅 런타임
1. **프롬프트 조립 순서**(캐시 친화적으로 고정부 → 가변부):
   1) 플랫폼 공통 시스템 규칙(안전·출력 형식) 2) `system_prompt` 3) 등장인물 카드 4) 상시(always-on) 설정집 5) `output_rules` + `status_template` + 이미지 코드 목록(코드+설명) 6) 예시 대화 ── 여기까지 캐시 대상 ── 7) 선택한 시작 상황의 `hidden_context` 8) 유저 페르소나 9) 장기기억(고정 메모 + 요약 + 벡터 검색 상위 k) 10) 키워드 매칭된 설정집 11) 최근 대화 N턴 12) 유저 입력
2. **토큰 예산**: 모델별 `max_context` 안에서 11)을 뒤에서부터 자르고, 잘린 부분은 요약 큐로 보내요.
3. **장기기억**: 20턴마다(설정값) 백그라운드 요약 → `memories(kind='summary')` + 임베딩(pgvector). 유저가 직접 쓰는 `memories(kind='pinned')`. 등장인물은 `kind='character'`로 상시 포함.
4. **키워드 트리거**: 최근 K턴(기본 3) + 유저 입력에서 키워드 매칭(대소문자·공백 무시, 정규식 옵션), 우선순위 순으로 예산 안에서 삽입.
5. **이미지 코드 렌더링**: 응답 스트림에서 `{{img:코드}}`를 서버가 검증(작품 자산에 있는 코드만)하고 클라이언트가 `<img>`로 렌더. 모르는 코드는 제거.
6. **상태창**: 응답 끝 ```status 코드블록을 분리해 별도 패널로 표시.
7. **재생성/분기**: 메시지는 `parent_id` 트리. 재생성 = 같은 부모의 형제 메시지 생성(재화 차감), 유저는 형제 간 스와이프. 과거 메시지에서 "여기서 분기"하면 새 `chat`이 `branch_from_message_id`로 생성.
8. **수정/삭제**: 유저 메시지 수정 시 이후 분기 생성. 삭제는 soft delete.
9. **스트리밍**: SSE(`text/event-stream`). 이벤트: `delta`, `image`, `status`, `ending`, `usage`, `done`, `error`.
10. **LLM 라우터**: `model_tiers` 테이블(basic/standard/premium) → 공급자 어댑터(OpenAI 호환 / Anthropic / Gemini). 키는 env 플레이스홀더. 개발 중에는 `LLM_PROVIDER=mock`(고정 응답)으로 비용 0.

### 1-4. 탐색
- 홈: 배너(관리자 지정), 신작, 급상승(24h 대화 수 증가), 장르별 레일, 이어하기.
- 랭킹: 일간/주간/월간 × 전체/캐릭터/스토리, 지표 = 고유 대화 유저 수 + 메시지 수 가중(materialized view, 1시간 갱신).
- 태그: 태그 페이지, 태그 필터(포함/제외).
- 검색: Postgres `pg_trgm` + 한국어는 간단히 `ILIKE`/trigram(제목·소개·태그·크리에이터명). 형태소 분석은 나중에.
- 19금 작품은 비인증 유저에게 목록에서도 숨김.

### 1-6. 안전

## 2. 아키텍처

```
[Vite+React SPA (iruka 재사용)] ──Privy JWT──▶ [Vercel Functions /api/*]
        │ SSE                                   │
        │                                       ├─ Supabase Postgres (+pgvector, pg_trgm, RLS)
        │                                       ├─ Cloudflare R2 (이미지, presigned PUT)
        │                                       ├─ LLM Router → OpenAI호환/Anthropic/Gemini/mock
        │                                       ├─ PG(포트원/토스페이먼츠 중 택1, [확인 필요]) 웹훅
        │                                       └─ Keeper(viem) → GIWA Sepolia: IrukaLedgerAnchor
        └─ Privy embedded wallet (서명만, 가스 없음)
Cron(Vercel): 기억 요약 큐, 랭킹 갱신, 장부 앵커링(1시간), 월 정산 마감
```

- 인증: 클라이언트 Privy access token → 서버에서 Privy 검증키로 JWT 검증 → `users.privy_did` 매핑. 서버는 Supabase **service role**로 접근하고 RLS는 방어선으로 둬요(클라 직접 접근은 공개 읽기만).
- 지갑 로그인 증명: 첫 로그인 때 임베디드 지갑 주소로 SIWE(EIP-4361) 메시지 서명 → 서버 검증 → `users.wallet_address` 바인딩. 가스 없음.
- 언어: 서버 `.mjs` 대신 TypeScript(`--experimental-strip-types` 이미 테스트에서 사용 중). Vercel Node 런타임.

## 4. 온체인 설계 (GIWA Sepolia → 메인넷은 출시 후 [확인 필요])

### 4-1. 선택지 비교
| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 양도 불가 ERC-20(SBT형 잔액) | 재화를 토큰 잔액으로 발행·소각 | 잔액이 체인에 그대로 보임 | 매 충전·차감마다 tx(메시지마다 가스), 유저 주소 잔액 공개=사생활, "토큰" 외형이라 가상자산 해석 리스크 [확인 필요] |
| B. 결제 영수증만 이벤트 기록 | 결제 1건 = 이벤트 1개 | 단순, 가스 적음 | 차감·잔액 검증 불가 |
| **C. DB 원장 정본 + 해시 체인 + 주기적 Merkle 앵커 + 결제 영수증 이벤트 (채택)** | DB `credit_ledger`가 정본, 각 항목은 이전 해시를 물고(해시 체인), 1시간마다 미앵커 구간 Merkle root를 GIWA에 커밋. 결제는 PG 검증 직후 영수증 해시를 즉시 기록 | 가스 최소, 개인정보 없음(솔티드 해시), 토큰 아님, 유저가 Merkle proof로 자기 거래 포함 여부 검증 가능, 운영자 사후 조작 탐지 가능 | 잔액 자체는 체인에서 직접 계산 안 됨(증명 기반) |

**채택: C.** 재화는 토큰이 아니고 양도·환전·출금이 불가능한 앱 내부 포인트예요. 체인은 "회사가 장부를 몰래 고치지 않았다"는 증명용이에요.

### 4-2. 컨트랙트 `contracts/src/IrukaLedgerAnchor.sol`
```solidity
// 상태 최소화: 이벤트 + 중복 방지 매핑
contract IrukaLedgerAnchor is AccessControl, Pausable {
  bytes32 public constant KEEPER_ROLE = keccak256("KEEPER_ROLE");
  mapping(bytes32 => bool) public receiptRecorded;
  uint64 public lastCheckpointToSeq;

  event PaymentReceipt(bytes32 indexed receiptHash, bytes32 indexed userCommit, uint64 crystals, uint64 amountKrw, uint64 paidAt);
  event PaymentRefunded(bytes32 indexed receiptHash, uint64 refundedAt);
  event LedgerCheckpoint(uint64 indexed fromSeq, uint64 indexed toSeq, bytes32 merkleRoot, bytes32 lastEntryHash);
  event SettlementCommitted(uint32 indexed period, bytes32 merkleRoot, uint64 totalCrystals);

  function recordPayment(bytes32 receiptHash, bytes32 userCommit, uint64 crystals, uint64 amountKrw, uint64 paidAt) external onlyRole(KEEPER_ROLE) whenNotPaused; // 중복이면 revert
  function recordRefund(bytes32 receiptHash) external onlyRole(KEEPER_ROLE); // 기록된 영수증만
  function commitCheckpoint(uint64 fromSeq, uint64 toSeq, bytes32 root, bytes32 lastEntryHash) external onlyRole(KEEPER_ROLE); // fromSeq == lastCheckpointToSeq+1 강제
  function commitSettlement(uint32 period, bytes32 root, uint64 total) external onlyRole(KEEPER_ROLE);
}
```
(OpenZeppelin 사용 여부는 Wave 0에서 결정. 없으면 최소 owner/keeper 직접 구현.)

### 4-3. 서버가 해시·서명하는 것
- `userCommit = keccak256(LEDGER_HASH_SALT || user_id)` — 주소·이메일을 체인에 올리지 않아요. 유저에게는 자기 `userCommit`과 salt 없는 검증 방법(서버가 proof 제공)만 보여줘요.
- `receiptHash = keccak256(abi.encode(provider, provider_payment_id, user_commit, amount_krw, crystals, paid_at))`
- `entry_hash = keccak256(prev_hash || seq || user_commit || delta || bucket || reason || ref_hash)` → Merkle leaf.
- 트랜잭션은 키퍼(`GIWA_KEEPER_PRIVATE_KEY`)가 서명·가스 지불. iruka `server/giwa/fulfillmentLease.mjs`의 리스 패턴으로 중복 전송 방지(Blob 대신 Postgres advisory lock/`ledger_checkpoints.state`).
- 유저 지갑 서명은 로그인(SIWE)에만 써요.

### 4-4. 결제 검증 흐름
1. 클라: `POST /api/payments/prepare {sku}` → 서버가 `payments(pending)`와 주문번호 발급.
2. 클라: PG 결제창(원화).
3. PG 웹훅 `POST /api/payments/webhook` → 서명 검증 → PG 조회 API로 금액·상태 재확인 → 트랜잭션 안에서 `payments.paid` + `credit_ledger(+purchase)` + `credit_accounts` 갱신.
4. 키퍼 큐가 `recordPayment` 전송 → `anchor_tx_hash` 저장.
5. 유저: 영수증 화면에서 tx 링크 + `GET /api/ledger/proof?entry=` Merkle proof로 검증.

### 4-5. 규제 메모 (모두 [확인 필요], 법률 자문 전 확정 금지)
- **선불전자지급수단(전자금융거래법)**: 자사 서비스 안에서만 쓰는 포인트라도 발행 잔액·사용처 범위에 따라 등록 의무 해당 여부가 갈릴 수 있음. 타 가맹점 사용·현금 환급 기능을 넣지 않는 것을 기본으로 함. [확인 필요]
